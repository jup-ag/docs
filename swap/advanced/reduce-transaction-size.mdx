When building custom transactions with `/build`, you may hit the 1232-byte transaction size limit, especially when adding custom instructions alongside the swap. The techniques below help, in order of how directly they target size.

<Tip>
If your wallet, SDK, and RPC support it, prefer a [Solana v1 transaction](/swap/advanced/transaction-versions) (`transactionVersion=1`). It raises the size limit to 4096 bytes and inlines up to 64 accounts without Address Lookup Tables, so it is usually the simpler fix than the techniques below, and Jupiter's newer features are built with the larger v1 size in mind. `maxBytes` is not supported with v1, because v1 already has the larger budget.
</Tip>

## Budget transaction bytes with `maxBytes`

Set `maxBytes` (integer, 1-1232) to ask Metis for a route whose swap transaction fits a byte budget. This is the most direct way to leave room for your own instructions.

```
GET https://api.jup.ag/swap/v2/build?...&maxBytes=1032
```

Sizing is deterministic, not an estimate. Metis picks the route by building and serializing its swap transaction the same way it would for the real swap, so a route it returns never exceeds the budget. If the swap ever exceeded `maxBytes`, that would be a bug. This makes `maxBytes` more accurate than `maxAccounts`, which only limits the account count as a proxy for size.

`maxBytes` is new and still experimental. If a returned route's swap exceeds the budget, or you hit any other issue, report it to [Jupiter developer support](https://support.jup.ag/requests/new) or the `#developer-support` channel in [Discord](https://discord.gg/jup).

### What the budget counts

The budget covers the **bare swap only**. Metis sizes a swap transaction with no extras, so these bytes are **not** counted today:

- Fields you pass to `/build`: `payer`, `feeAccount`, `destinationTokenAccount`, `nativeDestinationAccount`, the close authority, cashback, and the tip instruction.
- Anything you add yourself after `/build` returns: your own instructions, extra signers, and your own Address Lookup Tables.

Your final assembled transaction is therefore the bare swap plus everything above. Because those additions are deterministic and under your control, if you account for their bytes the total comes out exactly. Subtract their size from 1232 and pass the result as `maxBytes`.

<Warning>
  `maxBytes` budgets the bare swap, not your final transaction. The `payer`, close authority, `feeAccount`, destination accounts, tip, and your own instructions and lookup tables are **not** counted, so setting `maxBytes=1232` and then adding instructions will overflow the 1232-byte limit. Set `maxBytes` **below** 1232 by the size of what you add. As a reference, an extra signer (for example a separate `payer`) costs about 96 bytes, and a fee account costs 1 byte when a lookup table holds it or 32 bytes when it does not. Jupiter's own gasless path reserves a flat 200 bytes for its additions.
</Warning>

Setting `maxBytes` also changes how Metis sizes the route: omitting it uses an account-count model that never measures bytes, so `maxBytes=1232` is **not** a no-op and can return a different route than no limit at all.

### Before you use `maxBytes`

- **Use v0 transactions.** `maxBytes` with `transactionVersion=1` returns `400`. If you need v1, you do not need `maxBytes`, since v1 already raises the limit to 4096 bytes.
- **Leave headroom.** Pass `maxBytes = 1232 − (bytes of your additions)`. A small extra margin is wise where a cost is lookup-table-dependent (a key in a lookup table costs 1 byte, inline it costs 32).
- **Expect fewer routes.** Dynamic Swap routes are excluded when `maxBytes` is set. Check that pricing is still acceptable.
- **Handle `400`s.** Out of range (not 1-1232), non-integer, or `transactionVersion=1` all return `400`.

`/build` is ExactIn only, so the ExactIn-only restriction on `maxBytes` never affects it.

## Limit accounts with `maxAccounts`

Set `maxAccounts` (1-64, default 64) to limit the number of accounts in the swap route. Lower values produce simpler routes with fewer accounts. Reach for this when your constraint is the account count itself (for example CPI account limits), or as a retry lever alongside `maxBytes`. When the constraint is transaction size, prefer `maxBytes`, which targets bytes directly.

```
GET https://api.jup.ag/swap/v2/build?...&maxAccounts=20
```

Setting `maxAccounts` too low will severely degrade routing quality. Very low values (for example below 50) can result in **no route found** or **significantly worse pricing**, because the router cannot access enough DEXes or split the route across multiple pools. Start with a moderate reduction (for example reducing by 2 and retrying) and test pricing impact before going lower.

## Remove no-op setup instructions

The `/build` response always includes `createAssociatedTokenAccountIdempotent` instructions in `setupInstructions`, even when the token accounts already exist. These are no-ops on existing accounts but still consume transaction space.

To reclaim that space:

1. Check onchain if the associated token accounts already exist
2. If they exist, omit those setup instructions from your transaction
3. If they don't exist, keep the instructions

<Note>
  This technique requires an additional RPC call (`getAccountInfo`) per ATA you check. Depending on your RPC latency and how many ATAs the swap involves, this can add measurable overhead to your overall swap flow. Consider whether the space savings are worth the added latency for your use case, or batch the account checks in parallel or pre-swap.
</Note>

```typescript
import { findAssociatedTokenPda } from "@solana-program/associated-token";
import { TOKEN_PROGRAM_ADDRESS } from "@solana-program/token";

// Assumes @solana/kit imports and rpc from build/index.mdx example

// For each setup instruction, check if the target ATA already exists
// If it does, the createIdempotent instruction is a no-op and can be removed
const outputAta = await findAssociatedTokenPda({
  mint: address(outputMint),
  owner: address(taker),
  tokenProgram: TOKEN_PROGRAM_ADDRESS,
});

const accountInfo = await rpc.getAccountInfo(outputAta[0]).send();
const ataExists = accountInfo.value !== null;

// If ATA exists, filter out the createIdempotent instruction for it
const filteredSetupInstructions = ataExists
  ? build.setupInstructions.filter((ix) => {
      // Skip instructions targeting the existing ATA
      // Match by checking if any account in the instruction is the ATA address
      return !ix.accounts.some(
        (acc) => acc.pubkey === outputAta[0] && acc.isWritable
      );
    })
  : build.setupInstructions;
```
