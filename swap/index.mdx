The Swap API is Jupiter's REST API for swapping tokens on Solana, at `https://api.jup.ag/swap/v2`. One request returns a quote and, when you pass a wallet, a transaction ready to sign. Jupiter's routing engines compete for the best price on every request: Metis onchain routing, JupiterZ market makers answering a Request for Quote (RFQ), Dflow and OKX. You need no RPC node, no onchain state and no transaction assembly, and a single API key covers every Jupiter API.

Wallets, trading bots, AI agents, exchanges and payment apps integrate it through one of two paths:

- **Meta-Aggregator**: all routing engines compete for the best price. You get a fully assembled transaction, sign it, and Jupiter handles landing.
- **Router**: Metis onchain routing only. You get raw swap instructions with full transaction control for custom builds, CPI, and composability.

## Quick start

Get a quote for 0.1 SOL to USDC. No API key and no wallet are needed for a quote:

<CodeGroup>
```bash Request
curl "https://api.jup.ag/swap/v2/order?inputMint=So11111111111111111111111111111111111111112&outputMint=EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v&amount=100000000"
```

```json Response (quote only)
{
  "router": "jupiterz",
  "inAmount": "100000000",
  "outAmount": "12076477",
  "feeBps": 2,
  "transaction": null
}
```
</CodeGroup>

Without `taker`, `/order` returns the quote only. Add `taker=<your wallet>` to receive the transaction, sign it, and POST it to `/execute`. The full flow with `@solana/kit` and `@solana/web3.js` examples is on [Order and Execute](/swap/order-and-execute).

<Tip>
Keyless requests are limited to 0.5 requests per second. For production, pass an API key in the `x-api-key` header. See [Rate Limits](/portal/rate-limits).
</Tip>

## How a swap works

<Tabs>
  <Tab title="Meta-Aggregator">
    <Steps>
      <Step title="Get an order">
        `GET /order` with `inputMint`, `outputMint`, `amount` and `taker`. The response contains the quote, the winning `router`, a `requestId` and a base64 transaction.
      </Step>
      <Step title="Sign the transaction">
        Sign with the taker's key, and sign promptly: RFQ quotes carry an `expireAt`, and every quote goes stale as prices move.
      </Step>
      <Step title="Execute">
        `POST /execute` with the signed transaction and the `requestId`. Jupiter lands it and returns the result and signature.
      </Step>
    </Steps>
    Full code with `@solana/kit` and `@solana/web3.js`: [Order and Execute](/swap/order-and-execute).
  </Tab>
  <Tab title="Router">
    <Steps>
      <Step title="Get the instructions">
        `GET /build` with the same swap parameters. The response contains swap, setup and cleanup instructions, compute budget instructions and address lookup tables.
      </Step>
      <Step title="Assemble your transaction">
        Add your own instructions, simulate to set the compute unit limit, and compile a v0 transaction.
      </Step>
      <Step title="Sign and send">
        Send it through your own RPC, or through [`/submit`](/transaction/submit) with a SOL tip for Jupiter's landing pipeline.
      </Step>
    </Steps>
    Full code: [Build](/swap/build).
  </Tab>
</Tabs>

## Choosing a path

| | Meta-Aggregator | Router |
| --- | --- | --- |
| **Endpoints** | [`/order`](/swap/order-and-execute) + [`/execute`](/swap/order-and-execute#3-execute-the-transaction) | [`/build`](/swap/build) + [`/submit`](/transaction/submit) |
| **Returns** | Assembled transaction | Raw swap instructions |
| **Routers** | All (Metis, JupiterZ, Dflow, OKX) | Metis only |
| **Best for** | Most integrations. Best price, simplest flow. | Custom transactions, CPI, composability. |
| **Transaction landing** | Managed via `/execute` (optimised slippage, priority fees, proprietary landing pipeline) | Self-managed via your own RPC, or via [`/submit`](/transaction/submit) with SOL tips for Jupiter's proprietary landing pipeline |
| **Swap fees** | Yes (Jupiter platform fee) | No |
| **Integrator fees** | Referral fees (referralAccount + referralFee) | Platform fee only (platformFeeBps) or DIY |
| **Gasless** | [Automatic gasless, or your own `payer`](/swap/advanced/gasless) | Use your own `payer` |
| **Transaction modification** | No | Full control |

**Start with the Meta-Aggregator.** It gives you the best price because all routers compete, including RFQ market makers who often beat onchain routing by 5-20bps on major pairs. Only use the Router if you need to modify the transaction.

## Routing engines

Jupiter's routing combines multiple engines and selects the best execution price across all of them, with a self-learning mechanism that automatically sidelines underperforming sources.

| Engine | Role | Availability |
| --- | --- | --- |
| **Metis** | Jupiter's onchain routing engine. Multi-hop, multi-split swaps across Solana DEXes. Also available as an [independent public good](https://metis.builders). | Meta-Aggregator + Router |
| **JupiterZ** | RFQ (Request for Quote) system where market makers compete to provide off-chain liquidity. Often beats onchain by 5-20bps on major pairs. | Meta-Aggregator only |
| **Dflow** | Third-party on-chain router. | Meta-Aggregator only |
| **OKX** | Third-party OKX liquidity. | Meta-Aggregator only |

<Note>
JupiterZ (RFQ) is not available on the Router path. It is available through the Meta-Aggregator, where it competes with the other engines.
- Jupiter runs safety and validation mechanisms between integrators and market makers, and market makers have last-look execution rights, which requires controlled transaction handling to ensure validity and prevent spam.
- Transactions routed through JupiterZ cannot be modified after they are returned, so use cases that require CPI, custom instructions, or any transaction modification must use the Router path.
</Note>

## Endpoints

Keyless requests work at 0.5 requests per second. Pass an API key in the `x-api-key` header for production rate limits; get one at [Portal](https://developers.jup.ag/portal).

**Meta-Aggregator**

| Method | Endpoint | Description |
| --- | --- | --- |
| GET | [`/swap/v2/order`](/swap/order-and-execute) | Get a quote and assembled transaction |
| POST | [`/swap/v2/execute`](/swap/order-and-execute#3-execute-the-transaction) | Execute a signed `/order` transaction with managed landing |

**Router**

| Method | Endpoint | Description |
| --- | --- | --- |
| GET | [`/swap/v2/build`](/swap/build) | Get a quote and raw swap instructions |

## Migrating from Ultra or Swap API V1

Ultra Swap API users move to the Meta-Aggregator: `/order` and `/execute` replace Ultra's endpoints with the same managed landing. Swap API V1 (Metis) users on `/quote` and `/swap` move to `/order` for managed execution or to `/build` for raw instructions.

## FAQ

<AccordionGroup>

<Accordion title="Should I use the Meta-Aggregator or the Router?">
Start with the Meta-Aggregator (`/order` and `/execute`). All routing engines compete, including JupiterZ market makers, so it returns the best price, and Jupiter lands the transaction for you. Use the Router (`/build`) only when you must modify the transaction: adding your own instructions, calling the swap through CPI, or sending it through your own landing pipeline. The Router routes through Metis only and charges no Jupiter swap fee.
</Accordion>

<Accordion title="How do I get a quote without executing a swap?">
Call `GET /order` without `taker`. The response contains the full quote (`inAmount`, `outAmount`, `router`, `feeBps`, price impact) and `transaction: null`. This replaces the V1 `/quote` endpoint for price checks. Add `taker` when you want the transaction. See [Get an order](/swap/order-and-execute#1-get-an-order).
</Accordion>

<Accordion title="Do I need my own Solana RPC node?">
Not for the Meta-Aggregator: `/order` builds the transaction and `/execute` lands it, so the only thing you do yourself is sign. On the Router, you compile and send the transaction, through your own RPC or through [`/submit`](/transaction/submit), Jupiter's landing endpoint, which also removes the need for an RPC.
</Accordion>

<Accordion title="What fees does Jupiter charge?">
`/order` includes a platform fee that depends on the token pair: 0 bps when buying Jupiter tokens or swapping pegged assets, 2 bps SOL to stablecoin, 5 bps liquid staking token to stablecoin, 10 bps for everything else, and 50 bps on tokens less than 24 hours old. The fee is deducted from the quote and shown in `feeBps`, `platformFee` and `feeMint`. `/build` has no Jupiter swap fee. See [Fees](/swap/order-and-execute#fees).
</Accordion>

<Accordion title="Can I add my own fee to swaps?">
Yes. On `/order`, pass `referralAccount` and `referralFee` (50 to 255 bps); Jupiter keeps 20% of your fee and charges no separate platform fee. You create the referral accounts once through the [Referral Program](/tool-kits/referral-program). On `/build`, pass `platformFeeBps` with your `feeAccount`. See [Referral fees](/swap/order-and-execute#referral-fees) and [Build fees](/swap/build#fees).
</Accordion>

<Accordion title="Can users swap without holding SOL for gas?">
Yes, on `/order`. Three sources can make a swap gasless: Jupiter sponsors gas automatically when the taker has low SOL on an eligible trade, a JupiterZ market maker pays the fees on its own quote, or you sponsor gas by passing a `payer` wallet. Check `signatureFeePayer` against the taker to know which one applied. See [Gasless Swaps](/swap/advanced/gasless).
</Accordion>

<Accordion title="How are slippage and failed swaps handled?">
On `/order`, the Real-Time Slippage Estimator (RTSE) sets the slippage for each swap from token category, recent slippage data and live failure rates. On `/build`, pass `slippageBps=rtse` to opt in or a fixed value such as `50`. When `/order` cannot build a transaction it returns `transaction: ""` with an `errorCode` (for example insufficient funds or insufficient SOL for gas), and `/execute` returns its own error codes when landing fails. See [Slippage Estimation](/swap/advanced/slippage) and [Error codes](/swap/order-and-execute#error-codes).
</Accordion>

<Accordion title="How are priority fees set?">
On `/order` and `/execute`, Jupiter sets and pays attention to priority fees as part of managed landing. On `/build`, the response includes a compute unit price based on recent network fees; `computeUnitPricePercentile` lets you choose the percentile (`medium`, `high`, `veryHigh`, or a value in bps), with the 50th percentile as default and the 90th in `mode=fast`. Simulate to set the compute unit limit, and cap the price if you bid in volatile conditions. See [Compute Units](/swap/advanced/compute-units).
</Accordion>

<Accordion title="Can I send the transaction through my own RPC or a Jito bundle?">
Use `/build`. Its instructions are yours to assemble, sign and send however you want, and `forJitoBundle=true` excludes DEXes that are incompatible with Jito bundles. `/order` transactions are built for `/execute`: JupiterZ market makers have last-look rights and the transaction cannot be modified, so they are landed by Jupiter.
</Accordion>

<Accordion title="What are the rate limits?">
Keyless: 0.5 requests per second. Free API key: 1 RPS, Developer 10, Launch 50, Pro 150. `/execute` has its own bucket (Keyless 20, Free 50, paid plans 100 RPS) that does not count against your main limit. See [Rate Limits](/portal/rate-limits).
</Accordion>

<Accordion title="I use Swap API V1 or Ultra. What changes?">
V1's `/quote` and `/swap` become `/order` and `/execute` (or `/build` if you used `/swap-instructions`); route plans report `bps` instead of `percent`, and V2 instructions no longer emit fee events. Ultra's order and execute endpoints map directly onto `/order` and `/execute`. The migration guides list every change: [Ultra to Meta-Aggregator](/swap/migration/ultra-to-order), [Metis to Meta-Aggregator](/swap/migration/metis-to-meta-aggregator), [Metis to Router](/swap/migration/metis-to-build).
</Accordion>

</AccordionGroup>
